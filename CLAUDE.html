CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Build & test

All commands run from harvey/ (this directory).

make build          # builds all programs into bin/
go test             # run the package tests (fast, no Ollama required)
go test -run TestX  # run a single test or pattern
go test -race       # race-detector run before any commit
go build -o bin/harvey cmd/harvey/*.go
go build -o bin/assay  cmd/assay/*.go
cmt codemeta.json version.go  # regenerate version.go after bumping codemeta.json

testout/, bin/, dist/, man/ are gitignored build artifacts — never commit them.

Two executables

Binary Source Purpose
bin/harvey cmd/harvey/main.go → harvey.go Interactive terminal agent
bin/assay cmd/assay/main.go (standalone) LLM evaluation harness

cmd/assay/main.go imports the root harvey package for the Ollama client. It is otherwise self-contained.

Documentation convention

Every exported Go symbol must have a /** ... */ block comment with a description, Parameters:, Returns:, and Example: section. See any function in rag_support.go for the required format. This is enforced by project convention, not a linter.

version.go is generated by cmt — do not edit it by hand.

INSTALL.md is hand-maintained — do not run cmt codemeta.json INSTALL.md. The installer scripts (installer.sh, installer.ps1) have been removed; do not add them back until Harvey distributes pre-built binaries.

Agent lifecycle (terminal.go → Run)

The startup sequence wires state in this order, and order matters:

  1. Banner → workspace init → LoadHarveyYAML (path overrides) → KB → model cache
  2. Session picker → system prompt → skills catalog → backend selection → debug log
  3. Session resume / --continue / replay
  4. Auto-record → workspace-profile onboarding (once, if empty)
  5. REPL loop

The REPL chat path (histLenBeforeChat pattern):

histLenBeforeChat := len(a.History)
RunToolLoop or Chat → may grow History with tool call/result pairs
noToolCalls := len(a.History) == histLenBeforeChat   // captured BEFORE AddMessage
...
a.AddMessage("assistant", buf.String())
// inject prose-tool-call correction if needed
if noToolCalls { a.autoExecuteReply(...) }           // skipped after tool calls

noToolCalls must be captured before a.AddMessage because after that call the lengths are never equal.

Tool call dual path

Harvey has two separate execution paths depending on model capability:

Structured tools (RunToolLoop in tool_executor.go): used when the model returns proper tool_calls in the API response. Multi-turn: LLM → tools → results appended to history → LLM again.

Prose tool calls (tryExecuteProseToolCalls in terminal.go): used when small models emit JSON fenced blocks instead of structured calls. Single-turn only. Returns (dispatched bool, unknownNames []string). When dispatched is false, Harvey prints the “try /tools off or a larger model” warning. When unknownNames is non-empty, available tool names are printed and a correction message is injected into history after the assistant message.

autoExecuteReply (the tagged-fence block writer) is skipped when !noToolCalls — this prevents display-only code blocks in tool-call responses from being offered as files to write.

Three-silo memory architecture

Harvey has two independent knowledge stores, unified at retrieval time by UnifiedMemory.Recall():

Silo Files Content Injection point
Memory store memory_store.go, memory_miner.go, memory_manifest.go, agents/memories/ Typed experience records extracted from sessions Session start via UnifiedMemory.Recall()
Knowledge base github.com/rsdoiel/knowledge (external module, a normal versioned require in go.mod; no replace), agents/knowledge.db Hand-authored projects/observations/concepts (relational) Optional, also via UnifiedMemory

UnifiedMemory.Recall() queries both silos in priority order: workspace_profile + project_fact first (always injected, score 1.0), then experiential memories (FTS5), then KB observations. Token budget is enforced.

Memory mining flow: Manifest.UnminedSessions() finds .spmd files not yet in the manifest → Miner.Mine() sends session text to LLM for JSON extraction → interactive review → MemoryStore.Save() writes typed Fountain files. Auto-mines on session exit when sessionTurns >= 10.

Session recording — the session log

Each session writes an append-only JSONL log, agents/sessions/<stem>.jsonl (schema: notes/session-log-schema-as-built.md, DR-0038 to DR-0041), with large payloads spilled to <stem>.blobs/. The .spmd Fountain file beside it holds only the title page during the session; at close finishSession renders it from the log (sessionrender.go, sessionfile.go), and RecoverSessionFiles renders any left by a crash at startup. FOUNTAIN_FORMAT.md documents the output.

  • Log an event through the Agent.log* helpers (sessionlog_agent.go, sessionlog_permission.go, sessionlog_kb.go); they are safe with no log open. Do not write Fountain from feature code.
  • --continue, /session use, --replay and the session list read the log (sessionload.go: LoadSessionInfo, ListSessions, ContinueFromSession); an old .spmd with no log falls back to parseFountainSession for one release.
  • A feature that writes files or runs commands records the author’s answer with logAuthorsAnswer; model calls are logged by the client hook (BeginModelCall), with withCallPurpose saying what a call is for.
  • Rendering changes need the golden files in testdata/fountain/ regenerated (UPDATE_GOLDEN=1 go test).

Assay evaluation tool (cmd/assay/)

bin/assay runs prompts from agents/assay/corpus.yaml against Ollama models and writes testout/assay-<timestamp>/report.md + results.json.

Flags of note: - --guide-file PATH and --guide-compare — run each prompt twice (base + a guide file as the system message) and show a per-check delta table - --category NAME — run only one category (e.g. ts-deno, go-crosswalk)

When adding corpus prompts, follow the narrow-prompt principle: one testable capability per entry, at least one automatable contains: check, and 2–4 human: review questions targeting the specific failure modes that matter.

Exit codes

Both binaries use the workspace exit-code convention (workspace DR-0003; the table is in the Laboratory CLAUDE.md, “Exit codes for command-line tools”): 0 ok, 1 negative, 2 usage, 65 data, 66 no_input, 69 unavailable, 70 internal, 73 cant_create, 74 io, 75 temp_fail, 77 no_permission, 78 config. exitcode.go is the classifier: constructors (Usagef, NoInputf, Dataf, …) and sentinels (ErrNotFound, ErrInvalid) classify at the source, ExitCodeFor(err) maps an error to its class, and an error nothing classified is 70, never 1. Never match message text to classify. Each main is a thin os.Exit(mainRun(...)); flagSpecs (harvey) and defineAssayFlags (assay) are the single lists of options, and flags_test.go in each cmd/ compares them with the OPTIONS section of the manual, so a new option needs its manual entry and its mistakes must be usage errors (2). The EXIT STATUS sections in HelpText and AssayHelpText list the codes each tool can return and are tested. harvey treats a session as non-interactive when stdin is not a terminal, or for --replay without --replay-continue; problems a person could fix in the session are then failures (harvey.yaml 78, no backend 69). assay finishes its run and exits with the class of the first failure; failing automatic checks are results (exit 0). Design and history: exit-codes-survey.md, exit-codes-plan.md.

Key invariants to preserve

  • ToolRegistry.Dispatch returns fmt.Errorf("unknown tool %q", name) — tryExecuteProseToolCalls detects this via strings.Contains(r.Content, "unknown tool").
  • suggestPathFromHistory returns "" when there are ≠1 path-like tokens in the last user message. The autoExecuteReply fallback only calls promptAction (the Y/n box, which also reports end of input; a caller that writes files must treat that as quit, never as yes) when a single candidate is found; otherwise it asks the user to type a path.
  • The mockLLMClient in tier3_test.go is the canonical test double for LLMClient — reuse it rather than creating new ones.
